# XMind 测试用例生成（5 层纯文本风格）

将需求拆解为分层测试点，并用 XMind 2.0 格式输出。采用**纯文本 5 层结构**（无「测试点：」「预期结果：」前缀）+ **界面文字『』标识**，对标用户实际脑图习惯。

## 何时使用
- 用户给了一张需求截图/PRD，要「设计测试点」「输出测试点脑图」
- 用户明确要求生成 XMind 格式用例
- 任何「从需求文档生成测试用例」的任务

## 核心约定（必须遵守）

### 5 层节点结构（纯文本，无前缀）

```
L0 根（需求名+版本，如【TD-AI】xxx）
└── L1 业务场景（如「极简非京东查得税号但通过其他client_id查得（极简落库）」）
    └── L2 测试分类（如「挡板」「jysj、zysx取值优先」「异常场景」）
        └── L3 测试条件（如「近12个月销售额>=50W and <100W」）
            └── L4 测试数据（如「jysj=60万，zysx=80万」）
                └── L5 预期结果（如「使用jysj=60万进行分档，不使用zysx」）
```

### 两种用例构造方式

| 函数 | 层级链 | 适用场景 |
|------|--------|---------|
| `C3(条件, 数据, 预期)` | L3→L4→L5 | 条件与数据可拆分 |
| `C2(条件, 预期)` | L3→L4 | 条件与数据一体，省略 L4 |

> **选择原则**：能拆分条件与数据的用 `C3()`，无法拆分的用 `C2()`。一个 L2 分类下可混用。

### ⭐ 界面文字标识规范（『』）— 强制，无例外

**适用范围：仅 L3 及以下节点（测试步骤/条件/数据/预期）。**
**L1 业务场景、L2 测试分类是归纳用的层级名，一律不框**——哪怕节点文字里引用了字段名/按钮名
（如 L2 写「任务状态流转」「停止任务控制」「清除筛选」）。（用户 2026-09-20 明确）

**判断标准（一句话）**：把需求文档/原型里的关键字引用到测试步骤中时，用『』框起来。

即：**这个词在需求文档或原型里有没有对应文字？有 → 框；没有（纯描述、口语化改写、动词化用法）→ 不框。**

| 场景 | 是否框 | 说明 |
|---|---|---|
| 需求里的字段名被引用 | ✅ | `『任务名称』模糊查询`、`展示『任务名称/导入文件/数据源(所选值)』` |
| 需求里的按钮/操作入口 | ✅ | `点『清除筛选』`、`点击『停止任务』`、`点『开始解析』` |
| 需求里的枚举值/下拉选项 | ✅ | `『任务状态』分别选『执行中/解析中/已完成/已停止/失败』` |
| 需求里的弹窗/页面/菜单名 | ✅ | `打开『新增覆盖度查询』弹窗` |
| 需求里的提示/报错文案（引用片段） | ✅ | `提示『仅支持 .xlsx』` |
| 需求里的导出列名 | ✅ | `『单税是否查得/单票是否查得/税+票是否查得』` |
| 把界面词当动词用 | ❌ | `不允许提交任务`、`解析失败`、`停止后查看进度`（描述行为，非引用按钮） |
| 需求里没有的文字（自行归纳的测试描述） | ❌ | `列表为空，无报错`、`两条链路互不影响` |
| 接口路径 / 接口号 / 字段码值 | ❌ | `getSupportedProduct`、1038084、`data.ZX301` |
| 测试数据值 | ❌ | 税号、金额、日期、文件名（`覆盖度查询导入_查询结果.xlsx`） |
| L1 业务场景名（场景概括） | ❌ | `筛选与列表展示`、`任务互斥与停止控制` |
| **L2 测试分类名（分类概括，即使引用字段）** | ❌ | `任务状态流转`、`停止任务控制`、`清除筛选`、`列表字段展示` |

**L1/L2 层级名一律不框**（即使引用了需求关键字）：`任务状态流转`、`数据源选择`、`停止任务控制`、`清除筛选`、`新增覆盖度查询弹窗`。『』只出现在 L3+。

**⭐ 并列关键字合并规则（用户明确要求，2026-09-20）**

多个关键字用 `/`（或 `、`）并列时，**只写一对『』**：开头一个『、结尾一个』，内部用 `/` 分隔。
**禁止**给每个词单独套『』——碎片化括号既啰嗦又割裂语义。

```
✅ 『任务名称/导入文件/数据源(所选值)/总税号数/查询进度/任务状态/创建人(中文)/创建时间』
❌ 『任务名称』/『导入文件』/『数据源』(所选值)/『总税号数』/『查询进度』/『任务状态』/『创建人』(中文)/『创建时间』

✅ 展示『任务名称/导入 Excel/数据源』三项
❌ 展示『任务名称』、『导入 Excel』、『数据源』三项

✅ 可下载解析结果 Excel（『税号/明文税号』）
❌ 可下载解析结果 Excel（『税号』/『明文税号』）

✅ 『单税是否查得/单票是否查得/税+票是否查得』三列与接口返回一致
❌ 『单税是否查得』/『单票是否查得』/『税+票是否查得』三列与接口返回一致
```

细节：
- 括号注释（如 `数据源(所选值)`、`创建人(中文)`）**跟在所属词后面**，写在『』内部，不要另起一对括号。
- 用 `、` 并列的一律改写成 `/` 放在同一对『』内，全图统一。
- 并列值来自同一控件时更要合并：`『任务状态』分别选『执行中/解析中/已完成/已停止/失败』`（外层是字段名，内层是选项，两对括号，不合并）。

**什么情况不合并**：两个『』之间隔着描述性文字（`『任务状态』分别选『执行中/解析中/已完成/已停止/失败』`、`点击『停止任务』后『任务状态』变为『已停止』`），
或两个关键字属于**不同字段但紧挨着**（`『覆盖度查询』『执行中』时新增解析任务` —— 分属任务类型和任务状态，合并会产生歧义）。

**其他约束**：
- 『』必须成对出现，禁止嵌套，禁止用 `「」`/`""`/`''` 代替。
- 字段名后紧跟的「列」可写在外侧：`『数据源』列展示 -`（不要写成 `数据源列`）。
- 同一字段名前后写法必须一致，不要一处框一处不框。

### 正确 vs 错误

| ✅ 正确（纯文本5层 + 『』） | ❌ 错误 |
|--------|--------|
| L3: 『任务状态』分别选『执行中/解析中/已完成/已停止/失败』 | 任务状态分别选执行中/解析中/已完成/已停止/失败 |
| L2: 任务状态流转<br>└ L3: 『任务状态』分别选『执行中/解析中/已完成/已停止/失败』<br>&emsp;&emsp;└ L4: 各自正确过滤出对应状态的任务 | L2: 『任务状态』流转（层级名不框）→ 状态选执行中/解析中 |
| L3: 列表『覆盖度查询』任务行<br>└ L4: 展示『任务名称/导入文件/数据源(所选值)/总税号数/查询进度』 | 展示『任务名称』/『导入文件』/『数据源』(所选值)/『总税号数』/『查询进度』 |
| L3: 『解析中』点击『停止任务』<br>└ L4: 『任务状态』=『已停止』，不再派发新的解析调用 | 解析中点击停止任务 → 状态变为已停止 |
| L3: 设置多项筛选后点『清除筛选』 | 设置多项筛选后点清除筛选 |
| L2: 挡板<br>└ L3: 近12个月销售额>=50W and <100W<br>&emsp;&emsp;└ L4: jysj=60万，zysx=80万<br>&emsp;&emsp;&emsp;└ L5: 使用jysj=60万进行分档 | `边界-50万整 → 测试点：金额=50万 / 预期结果：不满足` |

> 无界面关键字的纯后端/算法场景（如挡板测算、字段码值比对）保持裸文本，不要为了统一而硬加『』。

## 文件命名规范（必须执行）
生成的最终 `.xmind` 文件名**必须**遵循以下格式，无任何例外：

```
需求名_测试脑图.xmind
```

- `需求名`：从需求文档/截图/PRD 标题提取的需求主体名称，**去掉团队前缀**（`【余萍】`、`【TD-AI】`），**保留需求标识标签**（如 `【泾渭云YYYYMMDD】`、`v1.5` 版本号）。
- 示例：需求 `【余萍】【TD-AI】【泾渭云20260804】纳税H5增加登录身份提示` → 输出 **`【泾渭云20260804】纳税H5增加登录身份提示_测试脑图.xmind`**
- 禁止用法：`-测试点`、`_脑图`、随机时间戳、纯日期等旧式命名；**不带 `【TD-AI】` 等团队前缀**（前缀由流水线 Step5 上传前统一追加，避免双重前缀）。
- 禁止用法：`-测试点`、`_脑图`、随机时间戳、纯日期等旧式命名。
- 生成时统一用 `xmind_gen.make_output_name(req_name)` 产出文件名，避免手写出错；
  若 `build_xmind(root, req_name=...)` 传了 `req_name` 且未显式指定 `out_path`，会自动套用该命名。

## 工作流

### Step 1：需求解析与功能点穷举（防止遗漏）
1. **读取需求**：文档/图片/文字，提取被测对象、规则、阈值、时间窗口、边界。
   - 图片优先用 yescan-ocr-qoder 技能识别；识别失败/无 key 时直接 Read 图片提取文字。
2. **抽取界面关键字清单**（画『』必备产物，生成前先做）：
   把需求/原型里出现的**界面文字**逐条抄下来（原样，不要改写），存成 `ui.txt`（每行一个词）：
   - 列表列头、表单 label、表头单元格
   - 按钮 / 操作入口名称
   - 枚举值 / 下拉选项 / 状态标签
   - 弹窗 / 页面 / 菜单名
   - 导出文件列名、提示报错文案

   示例（覆盖度查询需求）：
   ```
   任务名称
   导入文件
   数据源
   ...
   执行中
   解析中
   已完成
   ```
   这份清单既是**写节点时的『』依据**，也是**Step 6 校验时的词表**，一举两得。
3. **功能点穷举**（详见 `references/method.md` §一）：
   - 逐条从需求中提取**所有功能点**，形成功能清单
   - **穷举原则**：
     - 每个动词 = 一个功能点（判断、查询、排除、记录、返回、推送...）
     - 每个阈值/条件 = 一个功能点（>=50万、近15天、状态=成功...）
     - 每个枚举值 = 一个功能点分支
     - 需求中的示例/数据样例 = 必须覆盖的功能点
     - **隐含功能点**：权限校验、并发控制、日志记录、异常兜底、数据精度、**UI 展示效果**（见 Step 2.5）
4. **功能点 → L1 业务场景映射**：将功能清单按业务流程归组为 L1 场景。

### Step 2：选择测试设计技术（系统化覆盖）
根据功能点特性，选用测试设计技术矩阵（详见 `references/method.md` §二）：

| 技术 | 适用场景 | 是否必做 |
|------|---------|---------|
| **等价类划分** | 输入域分类、枚举值 | ✅ 必做 |
| **边界值分析** | 阈值/范围/区间 | ✅ 必做 |
| **判定表/决策表** | 多条件组合逻辑 | ✅ 推荐 |
| **状态迁移** | 状态机/流程流转 | ✅ 推荐 |
| **场景法** | 端到端业务流程 | ✅ 必做 |
| **错误推测** | 异常/边界经验 | ✅ 必做 |
| **因果图** | 条件间依赖/互斥 | 可选 |
| **正交实验法** | 多参数组合 | 可选 |

> 每个功能点至少选用 1 种技术，有阈值必做边界值，有多条件必做判定表。

### Step 2.5：UI 展示效果清单（必做，最易漏的场景类别）

凡是**有页面展示**的需求（列表、表格、详情、弹窗、表单、进度、导出），必须逐条过一遍下面 7 类展示场景，
挑适用的落成用例。完整清单与写法示例见 `references/method.md` §九。

| 类别 | 必查要点（挑适用的落用例） |
|---|---|
| **① 无数据/空状态** | 首次进入无数据；筛选后 0 条；删除末页最后一条后回到哪儿；接口返回 `null`/`[]`/字段缺失；关联数据缺失（无创建人、无进度分母）；不得出现白屏 / `undefined` / `null` / `NaN` |
| **② 数据过多/超长** | 单元格超长文本（截断 + 悬浮看全文，行高不变）；列多 → 横向滚动、表头对齐；每页条数切换（数据量恰为 0/1/整页/整页+1）；大数据量加载性能与滚动；表头/分页在滚动中固定；数据实时刷新时列表不跳动 |
| **③ 加载态与交互态** | 首次加载 loading/骨架屏；刷新按钮 loading；请求失败 → 错误提示 + 重试入口（不留白）；按钮禁用态（置灰 + 原因提示）；防重复点击/重复提交；提交中禁止关闭弹窗 |
| **④ 数值与格式精度** | 大数分隔（850430 不显示为科学计数法）；百分比 0%/100%/超 100%/分母为 0（除零）；时间格式与时区、跨天；长税号/长数字不丢精度、不截断（导出尤其）；金额与小数位 |
| **⑤ 状态与文案准确性** | 状态标签文案、颜色与真实状态一致；置灰/只读态文案；提示、报错、二次确认弹窗文案完整可读；文案过长时换行/省略 |
| **⑥ 布局与适配** | 窗口缩放 / 小屏（1366×768）；浏览器缩放 80%~200%；侧边栏收起展开后表格自适应；弹窗小屏下可滚动、内容不被裁切 |
| **⑦ 边界交互** | tooltip/悬浮内容不被容器裁切；下拉选项过多可搜索可滚动；操作列按钮过多 → 折叠「更多」；导出/下载的下载中、下载失败、文件过大提示 |

写法要求（沿用 5 层 + 『』规则）：
- L2 分类名用业务语，**不要**写「边界值」「异常场景」这类方法论词，也不加『』，如 `列表空数据展示`、`长文本与列宽自适应`、`数值与时间格式展示`
- 空态/满态的**判定口径**必须写进预期：写清「展示什么」（文案/占位）而不是笼统写「正常显示」
- 例：
  ```
  L2: 列表空数据展示
  ├── C2("首次进入『极简覆盖度查询』无任何任务",
  │      "显示空状态提示，不显示表体、不报错")
  ├── C2("筛选条件命中 0 条任务",
  │      "显示无匹配结果提示，筛选区已填条件保留")
  └── C2("删除末页最后一条任务后刷新",
         "自动回到上一页；仅剩一页时回到空状态")

  L2: 长文本与列宽自适应
  ├── C2("『任务名称』超长（≥50 字符）",
  │      "单元格截断显示省略号，悬浮展示完整名称，行高不变")
  └── C2("列数超出可视区域",
         "出现横向滚动条，表头与内容列对齐不错位")
  ```

> **不要为了凑数硬加**：需求里没有列表/进度/弹窗等展示元素时不适用；
> 但只要有表格或状态展示，①②③④ 至少各落 1 条用例。

### Step 3：分层设计测试点
按 5 层结构设计：
- L1 业务场景 → L2 测试分类（按技术维度划分）→ L3 测试条件 → L4 测试数据 → L5 预期结果

**L2/L1 节点命名强制规范（用户明确要求，2026-08-31）**：
- 测试分类节点（L2）直接使用**业务名称**，**禁止**带测试设计方法前缀，如「等价类：」「边界值：」「判定表：」「场景法：」「幂等性：」「错误推测：」等
- ✅ 正确：`缺失 responseTime 修复`、`13 个月临界`、`count 校验分支`、`覆盖重跑`
- ❌ 错误：`等价类：缺失 responseTime 修复`、`边界值：13 个月临界`、`判定表：count 校验分支`
- 测试设计技术只用于设计过程（Step 2 矩阵），不体现在节点文本中

### Step 4：覆盖度自检（生成前必做）
逐条对照功能清单，确认每个功能点都有对应用例：
```
功能点             | 对应 L1→L2→L3   | 用例数 | 覆盖状态
效贷挡板-销售额判断 | 效贷→挡板→...   | 6     | ✅
采集时间窗口校验    | 效贷→时间窗→..  | 8     | ✅
税号排除规则        | 税号排除→...    | 0     | ❌ 遗漏！需补
```

**UI 展示效果必须单列一行自检**（Step 2.5 的 7 类，逐类标覆盖状态）：

```
UI 展示维度        | 对应用例                | 覆盖状态
① 无数据/空状态     | 列表空数据展示→...      | ✅
② 数据过多/超长     | 长文本与列宽自适应→...  | ✅
③ 加载态/交互态     | ...                    | ❌ 需补
```

**有 ❌ 的必须补齐后再进入下一步。**

### Step 5：构造节点树与生成文件
1. 用 `scripts/xmind_gen.py` 的 `N()`（普通节点）、`C3()`（3层用例）、`C2()`（2层用例）。
   - L0/L1/L2 用 `N()` 构造分组节点
   - L3 及以下用 `C3()` 或 `C2()` 构造用例节点
   - **脚本写完后先跑参数预检**（高频踩坑：3 参数误写成 `C2()`，运行到一半才报 TypeError）：
     ```bash
     python scripts/lint_case_args.py gen_xmind.py          # 只检查
     python scripts/lint_case_args.py gen_xmind.py --fix    # C2 三参数自动改 C3
     ```
2. `build_xmind(root, out_path)` 或 `build_xmind(root, req_name=...)` 输出 `.xmind`。

### Step 6：层级、用例数与『』校验
1. **层级与用例数**：解析生成的 xml，确认最大层级为 L5（无多余 L6），统计用例数正确。
2. **界面文字『』校验**（必做，可脚本化）：
   ```bash
   python scripts/lint_brackets.py 输出文件.xmind --keywords ui.txt --all
   ```
   - **ERROR**：
     1. 『』不成对 / 嵌套 / **枚举值列表未包裹**
     2. **碎片化包裹**——`『A』/『B』`、`『A』、『B』` 这类并列词各自套括号（应合并为一对『』）
     3. **L1/L2 带『』**——场景/分类名不框，『』只允许出现在 L3+
   - **HINT**：命中界面词表但未包裹（泛动词居多，含描述性用法，需人工判断，不失败）
   - 用 Step 1 抽出的 `ui.txt` 做词表，命中率最高
   - HINT 逐条人工过：属于「需求关键字被引用」的必须补『』；属于动词化用法/测试数据的可忽略
   - 想让它当 CI 卡口：加 `--strict`（HINT/WARN 也算失败）

## 设计要点（避免踩坑）
- **功能点穷举是第一要务**：先从需求中提取所有功能点（F01/F02...），再按功能点设计用例。不做这步 = 必有遗漏。
- **UI 展示效果是最容易整类漏掉的（实测踩过）**：需求文档一般只写业务规则，不写「没数据长什么样」「名称超长怎么办」。只要涉及列表/表格/进度/弹窗，就必须按 Step 2.5 的 7 类清单过一遍，至少覆盖无数据、数据过多、加载态、格式精度四类。漏了这几类，评审时必被挑。
- **先定区间开闭，再写边界用例**：如「近15天-近45天」需明确是闭区间 `[15,45]`，否则易写出自相矛盾的用例（详见 `references/method.md` 的「边界值反例」）。
- **时间窗口统一用「距今天数 N」表述**，禁止「近X天±1天」这种歧义写法。
- **组合场景覆盖笛卡尔积**：多条「满足其一」规则要枚举全满足/仅一条/两条/全不满足。
- **异常兜底明确**：接口超时、null、空、数据类型异常，预期结果写清「视为不满足 / 挡板拦截 / 触发兜底」。
- **层级控制**：`C3()` 和 `C2()` 必须直接挂在 L2 分类节点下，不要在中间再加一层 N() 子分类，否则会多出 L6 层。
- **C2/C3 签名坑（实测踩过）**：`C2()` 只接受 2 个参数（条件, 预期），带测试数据必须用 `C3()`；写脚本前先确认函数签名，不要凭直觉传 3 个参数给 `C2()`。
- **节点文本禁止设计方法前缀**：L1/L2 节点名不得出现「等价类：」「边界值：」「判定表：」「场景法：」「幂等性：」等前缀，方法只用于设计过程（见 Step 3 命名规范）。
- **界面文字必须加『』（实测踩过）**：把需求/原型里的关键字（字段名、按钮、枚举值、弹窗名）引用到步骤中时，一律用『』框起来。判断标准是「这个词在需求里有没有对应文字」——有就框，动词化用法/纯描述不框。漏加会导致评审时分不清「界面选项」和「测试步骤」，例如把 `执行中/解析中` 当成测试步骤而非状态标签。生成后跑 `scripts/lint_brackets.py` 兜底。
- **『』只用于 L3+，L1/L2 不框（实测踩过）**：L1/L2 是场景/分类名，属于归纳性文字，即使引用了字段名也不加『』（写「任务状态流转」「停止任务控制」而不是「『任务状态』流转」）。lint 会把 L1/L2 带括号报为 ERROR。
- **并列关键字只写一对『』（实测踩过）**：`『A』/『B』/『C』` 是错的，必须写成 `『A/B/C』`；`、` 并列同理。碎片化括号是高频返工点，lint 会报 ERROR。括号注释（`数据源(所选值)`）跟在词后、写在『』内。仅当两个『』之间隔着描述性文字（`分别选`、`点击…后`）或分属不同字段时才保留两对。
- **隐含功能点不遗漏**：权限校验、并发控制、日志记录、数据精度、幂等性——这些需求文档不一定写但测试必须覆盖。
- **输出路径坑（实测踩过）**：`build_xmind(root, req_name=...)` 内部用 `make_output_name()` 产出的 out_path 是**相对路径**，文件会落在进程 CWD 而非需求文档目录。正解：显式拼绝对路径，`out_path = os.path.join(需求目录, make_output_name(REQ_NAME))`，再 `build_xmind(root, out_path=out_path)`，这样既遵守命名规范又落到预期目录。
- **Windows 控制台编码坑（实测踩过）**：脚本里 `print()` 中文/emoji（如 `✅`）在 stdout 被重定向时按 GBK 编码，会抛 `UnicodeEncodeError`。正解：**不要依赖 print 回读结果**，把 `{path, size, test_cases}` 写入 `result.txt`（`encoding="utf-8"`）后用 Read 工具读取。
- **文档目录中文路径**：无需转义，`os.path.join()` 直接传中文绝对路径即可正常读写。

## 校验方法（生成后必做）
```python
import zipfile, xml.etree.ElementTree as ET
xmind_path = "输出文件.xmind"
with zipfile.ZipFile(xmind_path) as z:
    content = z.read("content.xml").decode("utf-8")
root = ET.fromstring(content)
NS = "{urn:xmind:xmap:xmlns:content:2.0}"
def count_levels(elem, depth=0, counts=None):
    if counts is None: counts = {}
    if elem.tag.replace(NS,"") == "topic":
        counts[depth] = counts.get(depth,0)+1
        for c in elem: count_levels(c, depth+1, counts)
    else:
        for c in elem: count_levels(c, depth, counts)
    return counts
sheet = root.find(f"{NS}sheet")
counts = count_levels(sheet.find(f"{NS}topic"), 0)
print("各层级节点数:", dict(sorted(counts.items())))
# 期望：最大 L5，无 L6；L5 节点数 = C3 用例数，L4 中 C2 预期数 = C2 用例数
```

生成后建议追加**命名规范校验**：遍历 L1/L2 节点文本，确认无「等价类：」「边界值：」「判定表：」「场景法：」「幂等性：」「错误推测：」等设计方法前缀残留。

同时跑一次**界面文字『』校验**（见 Step 6）：
```bash
python scripts/lint_brackets.py 输出文件.xmind --keywords ui.txt
```
