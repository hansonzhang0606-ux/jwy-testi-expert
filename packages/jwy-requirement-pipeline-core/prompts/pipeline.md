# 泾渭云五步编排

1. Step1：需求确认，调用 `modules/requirement-analysis-docx/`。
2. Step2：代码分析，可选，调用 `modules/code-analyzer/`。
3. Step3：必须选择一项：选项1 测试脑图、选项2 接口脑图、选项3 DMP 用例脑图。
4. Step4：仅 Step3-选项1/2 后允许，调用 `modules/xmind-to-testcase/`。
5. Step5：可选 Confluence 归档；配置缺失、匹配不唯一或无权限时停止并说明原因。

每步完成后执行 `scripts/pipeline_state.py record`。工时适配只读取状态中 `tracking.eligible` 的 P 标识，禁止将未执行的可选步骤或未选择的 Step3 分支判为漏记。

## 用户故事信息（PRJ 编号 + 故事名称，缺一不可）

工时入库需要完整的用户故事标识，统一写成 **`<PRJ 编号>-<故事名称>`**：

- **PRJ 编号**：需求编号，形如 `PRJ-00884552`，**只能由测试人员提供，禁止猜测或编造**。
- **故事名称**：需求文档标题/文件名中的需求名（去掉团队前缀 `【余萍】`/`【TD-AI】`），保留需求自身标签，如 `【泾渭云20260915】修改泾渭云使用中台数据库账号`。

正确示例：`PRJ-00884552-【泾渭云20260915】修改泾渭云使用中台数据库账号`

**规则（强制）**：

1. **入口即确认**：本次需求第一次交互开始，先与测试人员确认这两部分，拼成完整用户故事串；会话内 P1~P5 所有步骤与工时记录**统一复用同一串**，不得中途换写法。
2. **只给一部分就追问**：测试人员只提供 PRJ 编号、或只提供故事名称时，**停下不推进**，明确提示：
   > ⚠️ 工时入库需要「PRJ 编号 + 故事名称」两部分信息，缺一不可。当前只提供了「<已给部分>」，请补充「<缺失部分>」。
3. **不得臆断**：故事名称可从需求文档标题/文件名推断，但必须**复述给测试人员确认**后再用；PRJ 编号缺了就问，不允许填占位符或猜测。
4. **脚本层兜底**：缺少任一部分时，工时记录脚本会拒绝写入（退出码 2）并返回补齐提示（详见 `time-tracking/prompts/time_tracking.md`「用户故事完整性」节）；AI 不得用 `--allow-partial-user-story` 绕过。
